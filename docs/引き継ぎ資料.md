## 4. エンジンの要点(深く入る前に読むところ)

- `engine.js` が計算の全部(画面には触れない)。`ui.js` が画面。先読みは `mc-pool.js` と `mc-worker.js`。
- 推奨手:
  - 先読み無し(貪欲)は `stratB`。中身は `stratB0` で、重みは `PARAMS`(既定)。
  - 商材ごとの上書きは `PRESETS[key].params` に書き、`applyThreshold` が既定の重みに重ねる。
  - アプリは先読み(`stratMCAsync`・`mcPrepare`・`mcRollout`)を使う。先読みの中の試し打ちも、同じ重みで打つ。
- 主な重み:

  | 重み | 意味 |
  |---|---|
  | tcost | 下げた温度を費用に数える |
  | midare・midareW | みだれ打ちを使う |
  | turn・land | 特殊温度に着く手への加点 |
  | heat | 火力上げを始める温度の余裕 |
  | cap | 本会心の価値 |
  | rush | ゾーンへ押し込む手の抑制 |
  | mpm | 未到達1マスに残す集中力 |
  | boostAim・boostRes | 会心ターンのねらい打ち |
  | er | 戻りの仕上げのやり直し |
  | lastDP・ldp2 | 最後の1〜2マスの総当たり |

- ゲームの決まりで、間違えやすいもの(利用者の情報):
  - 会心が理想値を通り越す時は、理想値で止まる。すでに理想値以上のマスへの会心は動かない(miss)。
  - 温度は1000℃から始まる。威力は温度で変わる(`scaleUp`)。
  - 最初の1手には地金特性が乗らない。
  - 集中の地金: 400の倍数で消費が半分、200の倍数(400の倍数でない)で消費1.5倍・会心が出やすい。
  - 戻りの地金: 200の倍数で戻る。戻る量は 12〜16。
  - みだれ打ち: 使うマスからランダムに4回叩く(ゾーン内のマスにも当たる)。
- 大成功率の目安(`PRESET_RATES`)は、これまでの9商材にだけある。追加した商材には無い。

## 5. 大成功率の改善(このスレッドの最後の作業)

### 5-1. やったこと
1. 全169商材を、先読み無し・乱数テープ・種11・各100局で測った。50%未満は81商材(追加した商材は78)。
2. 失敗の形は2つあった。
   - 集中力が尽きて届かない(18商材)。値の大きい Lv75 の武器など。
   - 届くが、ずれの合計が許容誤差を超える(残りの大半)。許容誤差の小さい盾・アタマ・短剣など。
3. ネットの攻略情報も調べた。
   - 高レベル装備は、最初に火力上げを2回してから、まとめて叩く技で寄せる。
   - 集中力あたりの伸びは、みだれ打ち > 超4連打ち > 4連打ち > ななめ打ち > 3倍打ち > 上下打ち の順。
   - 熱風おろしは戻りを飛ばすのに使う。使いすぎると温度が足りなくなる。
   - 集中の地金は、寄せるのは半減ターン、狙うのは1.5倍ターン。
   - 出典: dqxikoan.blog.jp/archives/5708078、hiroba.dqx.jp の「ウェロアの冒険日誌」(地金別の打ち方)、
     professoriason.blog.jp/archives/3860948 など。
4. 原因(手順を追って確かめた):
   - 既定の重みでは tcost が 0 で、熱風おろし(-150℃)が安く見えて使いすぎ、火力上げに集中力を取られていた。
   - 集中の地金では、消費1.5倍の温度に、打撃の集中力の約4割を使っていた。
5. 重みの組を比べた(新しい160商材、種22・各100局、既定と同じ局どうし)。
   - far = `{tcost:0.017, midare:1, midareW:1.5}`
   - farB = 幽紋刀と同じ = `{tcost:0.017, cap:12, rush:0.9, heat:8, midare:1, midareW:1.5, mdc:0.5}`
   - tight = ブルーム・ランプと同じ = `{cap:24, adv:0.375, land:4.5, save:0, center:0, pr:0.4, boostPlan:0}`
   - farT = far + `{turn:0, land:0}`(2回目に、残りの66商材で比べた)
6. 商材ごとに、既定より z≥2 の案を選んだ。多くの案から選ぶと偶然でも選ばれるので、
   **選ぶのに使っていない種33・各200局**で確かめ直し、そこでも z≥2 だった17商材だけに入れた。
   - 結果の表は PR #29 の説明欄と、`engine.js` の `ITEM_PARAMS` の上のコメントにある。
7. 効かなかった案:
   - heat 12、boostRes 40、tcost 0.033(13商材で差なし、または悪化)。
   - turn 0 だけ(差なし)。
   - farT を他の60商材に入れる(42.9% → 41.5%、差なし)。

## 6. 確かめ方(手順とスクリプト)

- 成績テスト: `node tests/sim.js`(これまでの9商材。基準と照合。4コアで12〜19分かかった)。
  - 推奨手を変えたら、確かめたうえで `--update` を実行する。
  - 追加した商材は成績テストに入っていない。
- 1商材の分析:
  `node tools/analyze.js --preset 名前 --games 100 --tape 1 --seed 22 --params '{"tcost":0.017}' --log 記録.jsonl`
  - `--tape 1` にすると、同じ局どうしで比べやすい。
  - `--preset` には、追加した商材の名前(例:`コメットソード`)も使える。
  - **注意:** `--log` に同じファイルを渡すと、記録済みの局は打たずに飛ばす(続きから再開する機能)。
    設定を変えて比べる時は、必ず新しいファイル名にする(前のスレッドで、古い結果を読んで誤った)。
- 同じ局どうしの比べ方: 2つの `--log` を局の番号(`g`)で突き合わせる。
  片方だけ大成功した局の数を a 対 b とすると、z = (b − a) / √(a + b)。
  前のスレッドでは、scratchpad に次の集計スクリプトを置いていた(scratchpad は次のスレッドに残らない)。

```js
// node pair.js 記録A.jsonl 記録B.jsonl
const fs = require('fs');
const rd = f => Object.fromEntries(fs.readFileSync(f, 'utf8').trim().split('\n').map(JSON.parse).map(r => [r.g, r]));
const [x, y] = process.argv.slice(2).map(rd);
let n = 0, A = 0, B = 0, a = 0, b = 0;
for(const g in x){ if(!(g in y)) continue; n++; A += x[g].great; B += y[g].great;
  if(x[g].great && !y[g].great) a++; if(y[g].great && !x[g].great) b++; }
console.log(`n ${n} 大成功 ${A} → ${B} 片方だけ ${a} 対 ${b} z=${((b - a) / Math.sqrt(Math.max(1, a + b))).toFixed(2)}`);
```

- 組み込んだ後の確認: 重みをエンジンに入れたら、`--params` 無しで同じ種を打ち直す。
  確かめた時の記録と、局ごとに結果が一致することを確かめる(前のスレッドでは全局一致を確認済み)。
- 変更の後は `python3 tools/stamp.py`(ファイルの版の印)を実行してからコミットする。

## 7. はまったところ(繰り返さないために)

- **裏で動かした処理が、途中で全部止まった。**
  - nohup で動かした比較が、知らない間に止まっていた。
  - Bash の `run_in_background` で動かすと、終わった時(止まった時も)に通知が来る。
  - `--log` の記録は残るので、同じファイルで再開できる(設定が同じ時だけ)。
- `pkill`・`pgrep -f` の使い方によっては、自分のシェルを止めてしまう(終了コード144)。PID を指定して止める。
- シェルの変数を使った `rm` は止められることがある。`"${S:?}"` の形にするか、新しいディレクトリを使う。
- 先読みありの分析は1局に数分かかる。何百局も回すと何時間もかかる。
- 160商材×3案のように多くを比べて選ぶと、偶然 z≥2 になるものが10件ほど混ざる。
  必ず、選ぶのに使っていない種で確かめてから入れる。
